# v0.4.1 migration and behavior changes

v0.4.1 hardens assurance and release control around the existing Metriplane
product. It keeps the recorded, local, bounded, planar, observe-only product
boundary and does not add authority to control machinery or approve a physical
process.

## Product behavior

Existing `metriplane demo`, `doctor`, `atlas`, `external`, `replay`, `test`,
`incidents`, and `run` command names remain available. Atlas comparisons now
require compatible process rules, evaluation context, and observation coverage
before reporting improvement. Requirement assessment distinguishes satisfied,
violated, unresolved, and not-exercised outcomes. Older bundles without the new
assessment remain readable and are handled as insufficient evidence where the
comparison cannot be proved.

The sampled missing-state policy is now explicit. Completion at the threshold
remains completion, and a first observed arrival after a threshold without a
prior sampled deviation retains the existing sampled-policy behavior. This is
not a continuous-time guarantee.

## Maintainer release controls

Release operations now use connected, typed records from source freeze through
candidate identity, target and predecessor resolution, qualification, approval,
promotion planning and locking, target observation, exact-byte reconciliation,
retention, evidence-chain and last-known-good transitions, pointer/index
updates, later invalidation, and immutable recovery. Stale predecessors,
competing writers, substituted records, unsafe paths, replayed operations, and
false-success recovery attempts fail closed.

These interfaces do not confer live authority. Under the owner-approved
[v0.4.1 assurance scope](v0.4.1-assurance-scope.md), genuine non-author signing,
independently administered production stores, production external CAS/lock/LKG,
and multi-party privileged deployment proof are deferred to later assurance
milestones. Disposable fixtures demonstrate software behavior only and do not
convert any deferred live requirement into a pass.

## Traceability and change governance

The repository now maintains a deterministic bidirectional graph connecting
requirements, capabilities, code, tests, documentation, and rubric obligations.
Supported command-line rows have explicit success and failure, exit-status,
text/JSON, and output-artifact characterization. Task work orders, release
membership, and migration-delta records govern changes to semantic behavior,
goldens, and test obligations. Missing ownership, traceability, approval, or
currentness blocks the applicable gate.

Static membership does not establish runtime support. Support and compatibility
claims remain limited to their executed environment and fixture evidence.

## Version and fixture boundary

The candidate package version is `0.4.1`. External fixture manifests bind an
exact Metriplane evaluation version. Preserve historical v0.3.0 and
v0.4.0.post2 fixture trees; evaluate them under v0.4.1 only by creating a
separate disposable projection and recomputing its checksum inventory.

The published reference for before/after validation remains
`metriplane==0.4.0.post2`. A v0.4.1 candidate or release must be installed in a
separate environment and identified by its own retained artifact hashes.

## Research and release history

v0.4.1 does not replace or modify the frozen v0.2.0 SoftwareX artifact, DOI
`10.5281/zenodo.20736619`, checksums, or measurements, and it does not change
the TIM evaluated software boundary at v0.1.3. No v0.4.1 DOI is claimed.

The immutable `v0.4.0` failed attempt, retired unpublished `v0.4.0.post1`
candidate, and published `v0.4.0.post2` release remain historical records. No
artifact or receipt from those identities is relabeled as v0.4.1 evidence.
