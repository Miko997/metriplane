their artifacts is reused for post2. Post2 adds no product capability or
assurance claim.

## Install and run

Install the exact production package with:

```bash
python -m pip install "metriplane==0.4.0.post2"
metriplane demo --open
```

The package-contained demo remains camera-free and works headlessly without
`--open`. The external recorded-state path is available through:

```bash
metriplane external validate path/to/fixture
metriplane external run path/to/fixture --out external-run
```

## Known limitations and deferred work

- Metriplane accepts recorded, already-estimated state and supplied process
  rules. It does not establish that the source, simulator, sensor, coordinates,
  or zone labels are physically correct.
- The named repository fixtures do not establish generic compatibility with
  ManiSkill, robomimic, ROS 2, MCAP, MassRobotics, or arbitrary robotics data.
- Metriplane remains recorded, local, bounded, planar, and observe-only. It does
  not control a robot or machine, certify safety, or approve quality release.
- MP2-007, MP2-014, MP2-015, MP2-016, and MP2-017 are deferred to v0.4.1
  Assurance Hardening. v0.4.0.post2 does not pass, complete, or waive them and
  does not complete the v1.0 assurance programme.
- Historical v2.5.x authority packets are not used or recreated for this
  release.

## Publication reconciliation incident

Production workflow `34045289769` published and verified the exact retained
artifacts successfully. Its original final reconciliation job then failed
closed because GitHub represented later generated cleanup steps as `pending`
at the exact final-reconciliation boundary. The broker quarantined the existing
publication lease and check `101519549031`; no package was rebuilt, re-uploaded,
or retagged.

An independently qualified, narrowly scoped broker repair re-proved the exact
workflow, release commit and tag, protected state, seven rulesets, retained
hashes, live PyPI files, and fresh production install. The controlled recovery
deleted only the matching lease ref and updated the same App check to canonical
`completed/success/released`. The repair subsequently merged through protected
main as PR #105 and was deployed from exact protected main. Workflow
`34045289769` remains accurately recorded as publication-successful but not
globally green.

At GitHub Release creation time the credential-bearing, inactive Zenodo release
hook was removed and provider readback found no remaining Zenodo hooks. No
automatic Zenodo archive or v0.4.0.post2 DOI was created.
